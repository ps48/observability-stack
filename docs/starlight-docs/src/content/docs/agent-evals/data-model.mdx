Agent evaluation data is one OpenTelemetry **log-based event**, [`gen_ai.evaluation.result`](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-events/), one per evaluation result (grade). It goes through the OTLP logs path. Its trace context is the evaluated span: `traceId` + `spanId` (or none for trace- or session-level results without a span).

## The event envelope

Each event is one OTLP `LogRecord` with these fields:

- `EventName` set to `gen_ai.evaluation.result`. This is the top-level log record field, not an attribute.
- `Timestamp` set to when the evaluation finished.
- Severity `INFO` (9) and an empty body.
- Instrumentation scope set to the library that emitted the event, as OpenTelemetry defines it: `opensearch-genai-observability-sdk-py` / `-ts` with the SDK version for the SDKs. The evaluator is not the scope; it is recorded in `opensearch.evaluation.evaluator.*`.
- Resource attributes of the producer (`service.name`, ...).

All evaluation data is in the record's attributes.

## `gen_ai.evaluation.result` attributes

Standard [GenAI semantic convention](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-events/) attributes:

| Attribute | Type | When |
|---|---|---|
| `gen_ai.evaluation.name` | string | always |
| `gen_ai.evaluation.score.value` | double | numeric score |
| `gen_ai.evaluation.score.label` | string | label, low cardinality (`pass`, `fail`, `relevant`, ...). `pass` / `fail` is the producer's verdict |
| `gen_ai.evaluation.explanation` | string | evaluator rationale |
| `gen_ai.response.id` | string | evaluated completion, if known |
| `gen_ai.conversation.id` | string | evaluated session, if known |
| `gen_ai.agent.name` | string | evaluated agent, if known |
| `error.type` | string | the evaluator, or in a run the task, raised (no score) |

OpenSearch extensions under `opensearch.evaluation.*`. They cover fields that are still proposals in the semantic conventions, and will move to `gen_ai.*` names when those proposals merge:

| Attribute | Type | Values |
|---|---|---|
| `opensearch.evaluation.level` | string | `span`, `trace`, `session`, `tool_call` |
| `opensearch.evaluation.evaluator.name` / `.version` | string | evaluator identity |
| `opensearch.evaluation.evaluator.type` | string | `llm_judge`, `code`, `human`, `external` |
| `opensearch.evaluation.score.min` / `.max` | double | scale bounds |
| `opensearch.evaluation.score.direction` | string | `maximize`, `minimize` |
| `opensearch.evaluation.score.threshold` | double | pass threshold |
| `opensearch.evaluation.judge.trace_id` | string | the LLM judge's own trace |

A trace-level result (the trace is known but not the span) carries the evaluated trace as the record's own `traceId`, with no `spanId`.

In an offline run, a grade also carries `test.suite.name`, `test.suite.run.id`, `test.case.id`, `test.case.name`, and the run metadata. `test.suite.name` and `test.case.name` are OpenTelemetry [`test.*` attributes](https://opentelemetry.io/docs/specs/semconv/registry/attributes/test/); `test.suite.run.id` and `test.case.id` are proposed OTel attributes ([semantic-conventions#1262](https://github.com/open-telemetry/semantic-conventions/issues/1262), [semantic-conventions-genai#79](https://github.com/open-telemetry/semantic-conventions-genai/issues/79)).

When the run happens in CI, the grades and the agent root spans also carry the OpenTelemetry [CI/CD attributes](https://opentelemetry.io/docs/specs/semconv/registry/attributes/cicd/) `cicd.pipeline.name`, `cicd.pipeline.run.id` and `cicd.pipeline.run.url.full` (from GitHub Actions, GitLab CI or Jenkins).

When a case's task raises, the SDK records one result per declared scorer with `error.type` set to the exception class name and no score.

The agent's own root span in each test case is stamped with the same `test.*` ids in the span index.

## Storage: `otel-v1-genai-evaluation-*`

The stack's Data Prepper `otlp-pipeline` routes log records by `eventName`. `gen_ai.evaluation.result` records go to the `genai-evaluation-pipeline`, and every other log goes to the general logs index as before. The evaluation pipeline writes **daily indices** named `otel-v1-genai-evaluation-YYYY.MM.dd`. It installs the index template `genai-evaluation-index-template.json`, which sets these mappings:

- `attributes.gen_ai.evaluation.score.value` and `opensearch.evaluation.score.*` are `double`.
- Evaluation names, labels, levels, `test.*`, `error.type`, `traceId`, `spanId`, and `eventName` are `keyword`.
- `gen_ai.evaluation.explanation` is `text`, with a `keyword` sub-field (`ignore_above` 256).
- `time` and `@timestamp` are `date_nanos`.
- Other string attributes map as `keyword` and other whole numbers as `double` through dynamic templates. The template allows 2,000 fields per index (`mapping.total_fields.limit`).

The pipeline's only processor copies `time` to `@timestamp`. OpenSearch generates the document ids. To map another producer's fields onto these names, add processors yourself, as shown for [AgentCore](/docs/agent-evals/evaluation-integrations/#amazon-bedrock-agentcore).

The pipeline does not guess values. When a result has no level, readers treat it as `span` if it has a span id and `trace` otherwise. Who produced a result is the instrumentation scope name (`instrumentationScope.name`): `opensearch-genai-observability-sdk-*` for the OpenSearch GenAI SDKs, otherwise the producer's own scope.

The Helm chart ships the same pipeline, index template (as a ConfigMap), and init job as Docker Compose.

<Aside type="caution">
The init script's ISM retention policies cover spans, logs, and service maps, but not `otel-v1-genai-evaluation-*`. Daily evaluation indices are kept until you delete them, or until you add an ISM policy for the pattern.
</Aside>

## Joining results to traces

Results join to agent spans (`otel-v1-apm-span-*`) on `traceId`, plus `spanId` for span- and tool-call-level results. They join to sessions on `attributes.gen_ai.conversation.id` = the span attribute `gen_ai.conversation.id`.

Example PPL queries:

```sql
-- Count and mean per evaluation
source = otel-v1-genai-evaluation*
| where eventName = 'gen_ai.evaluation.result'
| stats count() as results, avg(`attributes.gen_ai.evaluation.score.value`) as mean
    by `attributes.gen_ai.evaluation.name`
```

```sql
-- Runs of a suite with their result and test case counts
source = otel-v1-genai-evaluation*
| where eventName = 'gen_ai.evaluation.result'
    and `attributes.test.suite.name` = 'quickstart-suite'
| stats count() as results, distinct_count(`attributes.test.case.id`) as cases
    by `attributes.test.suite.run.id`
```

## The evaluations dataset and app config

OpenSearch Dashboards reads evaluations through a **dataset** rather than a hard-coded index. The stack's init job (`opensearch-dashboards-init`) creates two saved objects in the Observability Stack workspace:

- **Evaluation Dataset - Local Cluster**: a logs dataset (index pattern) over `otel-v1-genai-evaluation*`, with time field `time` and schema mappings for `time`, `traceId`, and `spanId`.
- **`AgentEvals-Config-<workspace>`**: the Agent Evaluations app config. It is a `correlations` saved object that names the traces dataset and the evaluations dataset, and the Evaluations pages read their index from it.

  ```json
  {
    "type": "correlations",
    "attributes": {
      "correlationType": "AgentEvals-Config-<workspace id>",
      "title": "AgentEvals-Config",
      "version": "1.0.0",
      "entities": [
        { "tracesDataset": { "id": "references[0].id" } },
        { "evaluationsDataset": { "id": "references[1].id" } }
      ]
    },
    "references": [
      { "name": "entities[0].index", "type": "index-pattern", "id": "<traces dataset id>" },
      { "name": "entities[1].index", "type": "index-pattern", "id": "<evaluations dataset id>" }
    ]
  }
  ```

The **Settings** dialog on the Evaluations page edits the same object, so a dataset you pick there survives re-runs of the init job. The init job repoints the config only if one of its index patterns no longer exists. To use another cluster or index, create a logs dataset over it, or let Settings create one, and select it in Settings.
